# AgentPulse 运行手册

本手册介绍 AgentPulse 在本机环境下的安装部署、日常运维、网络配置与故障排查方法。

---

## 1. 系统定位与客户端关系

AgentPulse 的核心定位是将一台闲置的安卓手机转化为电脑旁专用的 AI Agent 硬件级只读监控屏。
它不是单一 Agent 的专属调试台，而是一套贯穿任务调度（FirstMate）、终端窗格（Herdr）与细粒度 Agent 执行流（Pi）的全局统一看板。

系统架构由一个核心服务与两个观察客户端组成：
- **监控服务 (`service/`)**：运行在 WSL2 Debian 环境中的只读后台服务，负责将 FirstMate、Herdr 和 Pi 三处数据源聚合成统一的数据模型，并通过 HTTP REST API 与 WebSocket 对外提供服务。
- **手机 App (`android/`)**：基于 Kotlin + Jetpack Compose 构建的原生 Android 客户端，是整个监控体系的主客户端，用于全天候呈现全局指标、任务状态、终端实时输出、事件流与三级分级告警。
- **Debian TUI (`tui/`)**：基于 Rust + Ratatui 构建的终端客户端，作为同一套服务的第二个对称客户端，供开发者在桌面终端内直接观察系统状态。

全链路坚持只读监控定位：
服务端与所有客户端均不向 Agent 下发控制指令、不修改任务流转状态、不接管终端输入。

## 2. 安装与部署

日常管理已全面统一至 `pulse` 命令行工具（代码位于 `deploy/pulse`）。
历史脚本路径 `data/agentpulse-run/start.sh` 仅作为环境异常时的底层兜底参考，日常运维请始终使用 `pulse`。

### 执行安装

在代码仓库根目录下执行安装脚本：

```bash
./deploy/install.sh
```

如果需要自定义安装路径或在安装时预设放行手机 IP，可以使用 `--dir` 和 `--allow` 参数：

```bash
./deploy/install.sh --dir ~/.local/share/agentpulse --allow 10.103.111.190
```

安装脚本会执行以下动作：
1. 创建安装目录结构（默认目录为 `~/.local/share/agentpulse`）。
2. 同步 `service/` 代码并安装 `pulse` 管理脚本。
3. 创建命令软链接至 `~/.local/bin/pulse`，使得在任何工作目录下均可直接调用 `pulse`。
4. 初始化独立的 Python 虚拟环境并安装运行所需依赖。
5. 初始化放行 IP 配置文件 `config/allowed-ip`。

安装完成后，可通过以下命令验证安装：

```bash
which pulse
```

输出应指向用户局部命令目录：

```text
~/.local/bin/pulse
```

## 3. 日常运维命令

日常管理统一使用 `pulse` 命令，每个子命令的使用场景与命令说明如下：

### 3.1 启动服务 (`pulse start`)

**什么时候用**：电脑或 WSL 重启后、或首次部署完成后启动监控体系。

```bash
pulse start
```

该命令会启动 7890 监控服务与 7891 下载服务，并应用 nftables 防火墙策略。
命令具备幂等性，服务已运行时不会重复启动进程。
如果目标端口被外部进程占用，会直接提示占用进程名与 PID。

### 3.2 查看状态 (`pulse status`)

**什么时候用**：日常巡检、确认服务是否正常存活、检查手机是否成功接入。

```bash
pulse status
```

该命令会集中打印进程 PID、端口监听、`/api/v1/health` 检查状态、已连接手机数量、当前放行 IP 与防火墙规则生效情况。

### 3.3 修改放行 IP (`pulse allow <ip>`)

**什么时候用**：手机连接 Wi-Fi 后因 DHCP 分配导致 IP 地址发生变化时。

```bash
pulse allow 10.103.111.190
```

该命令会自动校验 IPv4 地址合法性，将新 IP 写入 `config/allowed-ip`，并即时重载防火墙规则。

### 3.4 查看服务日志 (`pulse logs`)

**什么时候用**：手机端连接异常、排查接口报错或查看请求来源时。

```bash
pulse logs
```

可选参数与用法：
- `pulse logs`：查看监控服务最近 50 行日志。
- `pulse logs -f`：持续跟随监控服务的实时输出。
- `pulse logs download`：查看 APK 下载服务最近 50 行日志。
- `pulse logs download -f`：持续跟随 APK 下载服务的实时输出。

### 3.5 重启服务 (`pulse restart`)

**什么时候用**：服务代码有更新、修改了全局环境变量配置、或遇到异常需要重置时。

```bash
pulse restart
```

该命令会安全停止现有进程、清理旧防火墙规则，随后重新启动服务并载入最新规则。

### 3.6 停止服务 (`pulse stop`)

**什么时候用**：下班关机前、暂时不需要手机监控以节省系统资源时。

```bash
pulse stop
```

该命令会结合 PID 文件与 `/proc/<pid>/cmdline` 双重校验，安全终止监控进程与下载进程，并清理创建的 nftables 防火墙表。

### 3.7 卸载系统 (`pulse uninstall`)

**什么时候用**：不再需要本机部署、希望彻底清理服务目录与软链接时。

```bash
pulse uninstall
```

该命令会停止所有运行中的服务、清空防火墙表、删除 `~/.local/bin/pulse` 软链接并移除安装目录。

## 4. 网络与防火墙策略

监控服务运行在 WSL2 环境中，通过局域网与手机建立直接通信。

### 端口策略划分

系统监听两个端口，各自承担不同安全级别的任务：
- **7890 端口（监控服务数据面）**：严格受限。
  该端口承载核心 REST API 与 WebSocket 事件流，仅放行本机回环地址（`127.0.0.1`）与通过 `pulse allow` 明确登记的手机 IP。
  局域网内其他未授权设备的所有连接请求均会被防火墙直接丢弃（drop）。
- **7891 端口（APK 安装包下载服务）**：完全开放。
  该端口仅用于静态分发 Android 客户端安装包。
  由于手机在初次下载 App 时往往尚未配置或其 IP 可能随时变动，如果对 7891 端口施加 IP 限制，会导致用户在换 IP 后无法下载更新安装包。
  因此 7891 端口故意不绑定特定 IP，任何局域网设备均可自由拉取公开的 APK 文件。

### 防火墙规则管理

防火墙采用 Linux 原生 `nftables` 进行高效过滤，规则维护在独立的 `inet agentpulse` 表中，不干扰系统其他网络规则。
查看当前规则与命中计数：

```bash
sudo -n nft list table inet agentpulse
```

放行规则计数仅在新建 TCP 连接时递增；已建立的长连接由连接跟踪机制（`ct state established,related accept`）快速放行。
如需验证放行规则是否生效，建议在手机端或客户端重新发起连接。

## 5. 手机客户端安装与连接

手机客户端为闲置 Android 手机（Android 8.0+ / API 26+）设计。
详细构建说明、签名配置与高级参数请直接参阅项目文档 [android/README.md](../android/README.md)。

### 安装步骤

1. 确保电脑端监控服务与下载服务已通过 `pulse start` 正常运行。
2. 手机连接至与电脑同一 Wi-Fi 局域网。
3. 手机浏览器打开电脑下载地址（如 `http://<电脑局域网IP>:7891/`），下载并安装 `agentpulse-v1.1.0-debug.apk`。
4. 安装过程中如遇未知来源安装提示，进入系统设置勾选「允许来自此来源的应用」。

### 连接配置

1. 在手机上启动 AgentPulse App。
2. 点击应用顶栏右上角设置图标（⚙️）。
3. 在「主机 host」中输入电脑的局域网 IP（例如 `10.103.105.100` 或直接输入 `10.103.105.100:7890`），端口保持 `7890`。
4. 点击「保存」后，App 会立即刷新并重连，无需重启应用。

## 6. 分级排查顺序

当手机端显示「服务未连接」或数据异常时，请严格按以下由浅入深的步骤逐步定位：

```
┌─────────────────────────────────────────────────────────────┐
│                       标准排查路线图                        │
└─────────────────────────────────────────────────────────────┘
  第 1 步: pulse status        -> 检查服务整体概要与端口监听
        │ (进程缺失/端口未监听)
        ▼
  第 2 步: 检查服务进程与端口   -> ps / ss 确认进程与端口占用
        │ (进程正常、端口监听)
        ▼
  第 3 步: 本地 HTTP 健康检查  -> curl 127.0.0.1:7890/api/v1/health
        │ (本地健康检查 200 OK)
        ▼
  第 4 步: 防火墙与手机 IP 核实 -> pulse status 放行 IP vs 手机实际 Wi-Fi IP
        │ (放行 IP 不一致) -> pulse allow <手机实际IP>
        ▼
  第 5 步: 查看实时日志        -> pulse logs -f 确认是否有手机请求到达
```

### 第 1 步：运行 `pulse status` 查看系统整体概要

首先执行：

```bash
pulse status
```

- **正常表现**：监控服务与下载服务均显示「运行中」，端口处于「监听中」，健康检查为「200 OK」，放行 IP 与手机当前 IP 一致。
- **异常应对**：
  - 若服务显示「未运行」，执行 `pulse start` 尝试拉起服务。
  - 若端口显示「外部进程占用」，记下提示的 PID，用 `ps -p <pid> -o args=` 确认占用者并处理冲突。

### 第 2 步：核对底层进程与端口状态

如果 `pulse status` 报告异常，通过系统底层工具交叉确认：

```bash
ps -ef | grep -E "agentpulse_service|http.server" | grep -v grep
```

```bash
ss -ltnp 'sport = :7890 or sport = :7891'
```

- **正常表现**：看到 `uvicorn agentpulse_service:app` 进程监听 `0.0.0.0:7890`，`http.server` 进程监听 `0.0.0.0:7891`。
- **异常应对**：如果进程存在但监听地址为 `127.0.0.1`，说明启动时未指定绑定局域网，需执行 `pulse restart`。

### 第 3 步：执行本机健康检查

在电脑终端内直接向监控服务发起本地 HTTP 请求：

```bash
curl -s --noproxy '*' http://127.0.0.1:7890/api/v1/health
```

- **正常表现**：返回包含 `"status":"healthy"` 的 JSON 字符串。
- **异常应对**：若无法连接或连接被拒绝（Connection refused），说明监控进程内部崩溃或正在重启，继续查看日志排查。

### 第 4 步：检查手机当前 IP 与防火墙放行规则

手机端断联最常见的原因是路由器 DHCP 重新分配了手机 IP。
在手机 Wi-Fi 设置中查看手机当前分配到的实际 IP 地址。
比对 `pulse status` 中显示的「放行 IP」：
- **正常表现**：手机当前 IP 恰好等于放行 IP，且查看防火墙规则可看到对应的 accept 规则条目：
  ```bash
  sudo -n nft list table inet agentpulse
  ```
- **异常应对**：若手机 IP 已改变（例如从 `10.103.111.190` 变为 `10.103.111.195`），直接在电脑端执行命令放行新地址：
  ```bash
  pulse allow 10.103.111.195
  ```

### 第 5 步：查看实时日志分析网络与交互

确认防火墙放行后，观察是否有来自手机的请求进入：

```bash
pulse logs -f
```

- **正常表现**：手机触发刷新或心跳时，控制台实时打印来自手机 IP 的 HTTP 请求与 WebSocket 连接记录：
  ```text
  INFO:     10.103.111.190:53778 - "GET /api/v1/health HTTP/1.1" 200 OK
  ```
- **异常应对**：
  - 如果日志中完全没有任何手机请求到达，说明流量在电脑外部被阻断（例如手机与电脑未连接同一 Wi-Fi、路由器开启了 AP 隔离、或 Windows 宿主机防火墙阻断了入站连接）。
  - 如果日志中出现大量的 500 报错，说明采集器解析上游数据源时出现异常，需检查 FirstMate 或 Herdr 运行状态。

## 7. 当前已知限制

在当前版本中，运行本套系统需了解以下已知边界：
1. **无系统开机自启**：
   WSL2 重启或宿主机 Windows 重启后，运行环境不会自动恢复。
   每次重启后必须在终端中重新执行一次 `pulse start` 拉起监控服务、下载服务并重建防火墙规则。
2. **手机 IP 漂移问题**：
   在校园网或未配置静态 DHCP 绑定的 Wi-Fi 环境下，手机断开重连可能会被分配新的内网 IP。
   一旦手机 IP 变化，受防火墙保护的 7890 端口将阻断手机通信，需在电脑端手动执行 `pulse allow <新IP>` 重新放行。
3. **Windows 宿主机防火墙不可见**：
   WSL2 mirrored 网络模式直接共享宿主机 Windows 的物理网络接口。
   Windows Defender 或第三方安全软件的入站规则不在 WSL2 Debian 的可见与可控范围内。
   如果本机排查一切正常但手机无论如何无法连通，需要在 Windows 高级防火墙设置中检查 7890 与 7891 端口的入站权限。
4. **移动端通知仅限前台与活跃态**：
   Android 客户端未接入 FCM 或第三方系统推送中转通道，依靠与电脑的直连 WebSocket 维持实时事件通知。
   当手机操作系统因激进省电策略或内存紧张杀掉后台 App 进程时，通知将无法在后台主动弹出，需在手机系统设置中为 AgentPulse 开启「无限制电池优化」以保证前台挂机稳定性。
